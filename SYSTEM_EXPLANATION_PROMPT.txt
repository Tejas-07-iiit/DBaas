1. EXECUTIVE SUMMARY & PLATFORM VISION
================================================================================
Unified Multi-Database as a Service (Multi-DBaaS) is an enterprise-grade Database-as-a-Service platform engineered to provide a single, unified control plane and developer dashboard for provisioning, managing, monitoring, and querying heterogeneous database paradigms:
- Relational: PostgreSQL (ACID transactions, relational structures)
- Document: MongoDB (flexible schema, JSON/BSON documents)
- Vector: Qdrant (high-dimensional vector search, embeddings, RAG applications)
- Graph: Neo4j (relationship-centric networks, Cypher queries)

THE CORE PROBLEM:
Modern engineering teams deploy diverse database engines to support polyglot persistence (e.g., PostgreSQL for transactions, MongoDB for unstructured logs, Qdrant for LLM retrieval). Managing separate database vendors or cloud consoles leads to fragmented billing, inconsistent access controls, credential sprawl, network exposure risks, and complex operational overhead.

THE MULTI-DBAAS SOLUTION:
Multi-DBaaS consolidates all database operations into:
- One intuitive web interface (Next.js 16 + React 19).
- One secure API Gateway and Control Plane (NestJS + Prisma + BullMQ).
- One isolated, private infrastructure network (10.50.0.0/24 subnet).
- Unified multi-tenant RBAC, automated quotas, lifecycle tracking, and encrypted credential rotation.

================================================================================
2. CORE ARCHITECTURAL INVARIANT: "NESTJS IS THE SINGLE GATEWAY"
================================================================================
THE CARDINAL RULE:
Customers and external applications NEVER connect directly to customer database instances over the public internet.

- Traditional cloud DBaaS providers expose public IP addresses and open database ports (5432, 27017, 6333, 7474) protected only by firewall allowlists or public credentials.
- Multi-DBaaS fundamentally inverts this model: database instances live exclusively within an isolated private network (e.g., 10.50.0.0/24).
- The NestJS Backend is the SOLE gateway for both:
  1. Control-Plane Operations: Provisioning, starting, stopping, restarting, resizing, deleting, credential rotation, and configuration updates.
  2. Data-Plane Operations: Queries, mutations, and vector searches (submitted via authenticated HTTPS REST endpoints and forwarded internally to the database).

WHY THIS INVARIANT MATTERS:
1. Zero Public Attack Surface: Database engine ports are never exposed to public internet scanners, zero-day port exploits, or brute-force connection attacks.
2. Centralized Authentication & RBAC: Every single query and management operation is validated against Firebase Auth tokens and project membership permissions before reaching the database.
3. Metering & Quotas: Since all traffic transits the gateway, compute time, query volume, storage usage, and rate limits can be precisely metered and billed.
4. Total Auditability: All administrative actions and lifecycle operations produce immutable audit and event records.

3. SYSTEM ARCHITECTURE & 4-TIER HIERARCHY
================================================================================
Multi-DBaaS is structured across 4 distinct layers:

[LAYER 1: USER & CLIENT LAYER]
- Customer Web Dashboard: Next.js 16 (App Router), React 19, Tailwind CSS v4, TanStack Query.
- Customer Client Applications: Backend APIs and microservices interacting with databases via the NestJS Gateway REST API over HTTPS.

[LAYER 2: CONTROL PLANE GATEWAY (NestJS)]
- Single Entry Point: All external HTTPS traffic enters the NestJS Application.
- Authentication & Guard Layer: Verifies Firebase ID tokens (`FirebaseAuthGuard`).
- Multi-Tenant RBAC: ProjectAuthorizationService validates tenant ownership and team roles.
- Validation Engine: Runtime Zod validation pipes on all incoming payloads.
- Control-Plane Database: Platform PostgreSQL managed via Prisma ORM for storing users, projects, memberships, subscriptions, database metadata, operations, and audit logs.
- Asynchronous Task Queue: BullMQ with Redis for non-blocking, distributed job processing.

[LAYER 3: INFRASTRUCTURE ORCHESTRATION LAYER]
- Central Management VM: Dedicated management node (`10.50.0.2/24`) reachable over mutual TLS (mTLS) or private API tokens.
- Hypervisor / Container Runtime: KVM/libvirt on dedicated SSD storage or Kubernetes with isolated namespaces.
- Private Isolated Network: Subnet `10.50.0.0/24` with strict firewall/NetworkPolicy rules.
- Network Tunneling: WireGuard VPN tunnels establishing encrypted pathways between control plane routers and hypervisor nodes.

[LAYER 4: DATA PLANE LAYER]
- Isolated Customer Database Instances: Dedicated VMs or container workloads running certified engine binaries (PostgreSQL, MongoDB, Qdrant, Neo4j).
- Private IP Allocations: Dedicated internal addresses (e.g., `10.50.0.11`, `10.50.0.12`).
- Storage Subsystem: Dedicated Persistent Volume Claims (PVCs) or raw virtual disk images (QCOW2 on SSD).

5. IDENTITY, AUTHENTICATION & MULTI-TENANT RBAC
================================================================================
IDENTITY ARCHITECTURE:
- Authentication is offloaded to Firebase Authentication (supports Email/Password, Google OAuth, and social providers).
- Clients send the Firebase JWT in the `Authorization: Bearer <token>` header.
- The NestJS `FirebaseAuthGuard` decrypts and verifies the token using the Firebase Admin SDK.
- The `UserService` automatically synchronizes the user profile into the Platform PostgreSQL database upon first access, guaranteeing a local relational identity record.

AUTHORIZATION HIERARCHY:
Platform Level:
- USER: Standard authenticated developer or organization member.
- ADMIN: Platform administrator with global read/write visibility.

Project Level (Multi-Tenant RBAC):
Every resource (database, operation, event, member) belongs to a Project.
- OWNER: Full control over project, can delete project, manage billing, add/remove members, modify roles, and provision/deprovision databases.
- ADMIN: Can provision, modify, start, stop, restart, delete databases, rotate credentials, and invite members. Cannot delete the project or modify the Owner.
- MEMBER: Read-only access to database metadata, connection parameters, operations, events, and metrics. Cannot perform mutation or lifecycle actions.
- VIEWER: Read-only access for observability.

STRICT 404 DISCLOSURE POLICY (DEFENSE-IN-DEPTH):
To prevent cross-tenant enumeration, probing, and unauthorized discovery:
- If a user requests a database UUID belonging to Project B while authenticated under Project A, the API returns `404 Not Found` (NEVER `403 Forbidden`).
- If a user queries a project they do not belong to, the API returns `404 Not Found`.
- An attacker cannot determine whether a resource exists on the platform.

IMMUTABLE INFRASTRUCTURE FIELDS:
Public APIs reject all direct attempts to patch or write low-level infrastructure attributes:
- `internalIp`, `vmId`, `host`, `port`, `credentials`, `status`, and `failureReason` can NEVER be altered via public REST endpoints. They are exclusively managed by the internal lifecycle worker.

6. SUBSCRIPTION TIERS & TRANSACTIONAL QUOTA ENFORCEMENT
================================================================================
SUBSCRIPTION TIERS:
| Subscription Tier | Max Databases | Max CPU Cores | Max RAM (MB) | Max SSD Storage (MB) |
|---|---|---|---|---|
| FREE              | 2             | 4             | 4,096 (4 GB)  | 20,480 (20 GB)        |
| BASIC             | 5             | 16            | 16,384 (16 GB)| 102,400 (100 GB)      |
| PRO               | 20            | 64            | 65,536 (64 GB)| 512,000 (512 GB)      |

ATOMIC TRANSACTIONAL QUOTA ACCOUNTING:
To eliminate race conditions (such as concurrent requests attempting to exceed quota limits):
1. Quota checks occur inside a PostgreSQL serializable transaction using Prisma.
2. The system aggregates the current resource sum of all non-deleted databases for the project:
   `SUM(cpuCores)`, `SUM(ramMb)`, `SUM(storageMb)`, `COUNT(id)`.
3. If `currentSum + requestedProfile > tierLimit`, the transaction rolls back immediately with a `400 Bad Request / QuotaExceededException`.
4. Only upon successful quota verification is the database record inserted in `REQUESTED` state.

7. ASYNCHRONOUS PROVISIONING & DATABASE LIFECYCLE STATE MACHINE
================================================================================
Multi-DBaaS provisions real virtual machines and persistent volumes. Because hardware allocation takes several seconds or minutes, the platform uses an asynchronous, non-blocking lifecycle engine.

ASYNC WORKFLOW SEQUENCE:
1. Client issues `POST /api/v1/projects/:projectId/databases`.
2. NestJS validates RBAC and performs atomic quota checks.
3. NestJS persists `DatabaseInstance` in `REQUESTED` state and `DatabaseOperation` in `PENDING` state.
4. NestJS pushes a `provision-database` job to the BullMQ Redis queue.
5. NestJS immediately returns `201 Created` with `databaseId` and `operationId`. The HTTP connection is NOT held open.
6. The `DatabaseLifecycleConsumer` worker picks up the job:
   - Updates `DatabaseOperation` -> `IN_PROGRESS`
   - Updates `DatabaseInstance` -> `PROVISIONING`
   - Invokes `IInfrastructureProvider.provisionDatabaseVm()`
   - Polls or awaits hypervisor verification
   - Generates strong credentials and encrypts them via AES-256-GCM
   - Transitions `DatabaseInstance` -> `RUNNING`
   - Transitions `DatabaseOperation` -> `COMPLETED`
   - Logs `DatabaseEvent` (`STARTED` / `CREATED`)

FINITE STATE MACHINE (FSM):
```
                  ┌──────────────┐
                  │  [CLIENT]    │
                  │ POST /db     │
                  └──────┬───────┘
                         ▼
                  ┌──────────────┐
     ┌───────────►│  REQUESTED   │───────────┐
     │            └──────┬───────┘           │
     │ Retry             │ Worker picks up   │ Deletion/Error
     │                   ▼                   ▼
     │            ┌──────────────┐    ┌──────────────┐
     │            │ PROVISIONING │───►│    ERROR     │
     │            └──────┬───────┘    └──────┬───────┘
     │                   │ Verified          │ DELETE /db
     │                   ▼                   ▼
     │            ┌──────────────┐    ┌──────────────┐
     │    ┌──────►│   RUNNING    │───►│   DELETING   │
     │    │       └──────┬───────┘    └──────┬───────┘
     │    │              │                   │ VM & Disk Cleaned
     │    │ Restart/Start│ Stop              ▼
     │    │              ▼            ┌──────────────┐
     │ ┌──┴───────┐┌──────────────┐   │   DELETED    │
     │ │ STARTING ││   STOPPING   │   └──────────────┘
     │ └──┬───────┘└─────┬────────┘
     │    ▲              │
     │    │ Resume       ▼
     │    └───────┌──────────────┐
     │            │   STOPPED    │
     │            └──────────────┘
     └───────────────────┘
```

STATE DEFINITIONS:
- REQUESTED: Metadata persisted; queued in BullMQ.
- PROVISIONING: Worker allocating storage, cloning base image, configuring network.
- RUNNING: VM booted, database process responsive, credentials verified.
- STOPPING: Graceful shutdown initiated (ACPI / SIGTERM).
- STOPPED: VM powered down; persistent storage retained.
- STARTING: VM booting from existing disk.
- RESTARTING: Rebooting VM domain.
- DELETING: Deprovisioning VM, scrubbing storage volumes, releasing IP.
- DELETED: Soft-deleted record; all underlying infrastructure purged.
- ERROR: Infrastructure failure with diagnostic reason recorded in `failureReason`.

OPERATIONS TRACKING (`DatabaseOperation`):
Every lifecycle trigger (PROVISION, START, STOP, RESTART, DELETE) creates a tracked operation:
- `id`: Unique UUID.
- `type`: `OperationType` enum.
- `status`: `PENDING` -> `IN_PROGRESS` -> `COMPLETED` | `FAILED` | `CANCELLED`.
- `retryCount` / `maxRetries`: Exponential backoff retry handling.
- `providerOpId`: Infrastructure tracking ID.
- `errorDetails`: Stack trace or error message if failed.

8. INFRASTRUCTURE ORCHESTRATION & CENTRAL MANAGEMENT VM CONTRACT
================================================================================
THREE-TIER INFRASTRUCTURE HIERARCHY:
1. Control Plane Backend: NestJS orchestrator.
2. Central Management VM (`10.50.0.2`): Privileged gateway to KVM/libvirt hypervisor.
3. Dedicated Database VMs (`10.50.0.10 - 10.50.0.254`): Isolated customer database guests.

PROVIDER ABSTRACTION PATTERN (`IInfrastructureProvider`):
The NestJS backend interacts with infrastructure solely through a decoupled TypeScript interface:
```typescript
interface IInfrastructureProvider {
  provisionDatabaseVm(request: ProvisionVmRequest): Promise<ProvisionVmResult>;
  startDatabaseVm(vmId: string): Promise<VmActionResult>;
  stopDatabaseVm(vmId: string): Promise<VmActionResult>;
  restartDatabaseVm(vmId: string): Promise<VmActionResult>;
  deleteDatabaseVm(vmId: string): Promise<VmActionResult>;
  getVmStatus(vmId: string): Promise<VmStatusResult>;
  checkVmHealth(vmId: string): Promise<VmHealthResult>;
  reconcileVms(): Promise<VmReconciliationResult>;
}
```

THREE AVAILABLE PROVIDERS:
1. `MockInfrastructureProvider` (Default for local development and CI testing):
   - Zero external hypervisor dependencies.
   - Stateful in-memory simulation with realistic VM IDs (`vm-post-xxxx`) and private IPs (`10.50.0.x`).
   - Configurable failure triggers (`PROVISION_FAIL`, `START_FAIL`, `HEALTH_FAIL`) to test worker retries.
2. `LocalDevelopmentProvider`:
   - Returns simulated hardware data flagged with `isSimulated: true`.
3. `CentralManagementProvider` (Production implementation):
   - Secure HTTP client communicating with Central Management VM over mTLS / Bearer token.
   - Implements REST contract:
     - `POST /api/v1/vms/provision`
     - `POST /api/v1/vms/:vmId/start`
     - `POST /api/v1/vms/:vmId/stop`
     - `POST /api/v1/vms/:vmId/restart`
     - `DELETE /api/v1/vms/:vmId`
     - `GET /api/v1/vms/:vmId/status`
     - `GET /api/v1/vms/:vmId/health`
     - `GET /api/v1/vms/reconcile`

9. CREDENTIAL SECURITY & DATA PROTECTION
================================================================================
1. AES-256-GCM Symmetrical Encryption:
   - All generated database passwords are encrypted prior to storage in the `database_credentials` table.
   - Uses initialization vectors (IV) and authentication tags to guarantee integrity and confidentiality.
   - Plaintext passwords NEVER touch database storage.
2. Decrypted Retrieval on Demand:
   - When a Project Owner or Admin calls `GET .../databases/:id/connection`, the backend decrypts the password in memory and formats the official connection URI.
3. Credential Rotation:
   - Calling `POST .../databases/:id/credentials/rotate` generates a new cryptographically secure password, provisions it inside the database instance, archives the old credential record, and stores the new encrypted secret.

12. DATABASE SCHEMA & DATA MODEL SPECIFICATION
================================================================================
The Platform Control Plane PostgreSQL database is managed via Prisma ORM:

MODELS & RELATIONS:
1. `User`:
   - `id` (UUID), `firebaseUid` (unique string), `email` (unique string), `name`, `avatarUrl`, `role` (USER | ADMIN).
   - Relations: owns `Project[]`, belongs to `ProjectMember[]`, triggers `AuditLog[]`.
2. `Project`:
   - `id` (UUID), `name`, `description`, `ownerId` (FK -> User).
   - Relations: `members` (`ProjectMember[]`), `subscription` (`Subscription`), `databases` (`DatabaseInstance[]`), `auditLogs`.
3. `ProjectMember`:
   - `id` (UUID), `role` (OWNER | ADMIN | MEMBER | VIEWER), `userId` (FK -> User), `projectId` (FK -> Project).
   - Unique compound index: `[userId, projectId]`.
4. `Subscription`:
   - `id` (UUID), `tier` (FREE | BASIC | PRO), `status` (ACTIVE | CANCELED | PAST_DUE | TRIALING), `stripeCustomerId`, `stripeSubscriptionId`, `projectId` (FK -> Project, unique).
5. `DatabaseInstance`:
