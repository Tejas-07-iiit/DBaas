1. EXECUTIVE SUMMARY & PLATFORM VISION
================================================================================
Unified Multi-Database as a Service (Multi-DBaaS / M-DBaaS) is an enterprise-grade
cloud database orchestration platform designed to provide a unified developer
experience, single control plane, and unified gateway for provisioning, managing,
monitoring, and querying heterogeneous database engines:

- Relational Databases: PostgreSQL (ACID compliance, relational integrity, SQL)
- Document Databases: MongoDB (Flexible JSON/BSON documents, high-volume ingest)
- Vector Databases: Qdrant (High-dimensional vector search, semantic embeddings, RAG)
- Graph Databases: Neo4j (Relationship traversal, connected data graphs, Cypher)

THE MODERN ENGINEERING CHALLENGE:
Modern distributed software architectures embrace polyglot persistence. A single
microservice platform frequently requires PostgreSQL for transaction-critical user
accounts and ledger data, MongoDB for unstructured telemetry, and Qdrant for AI
semantic search. Managing multiple cloud database vendors or isolated self-hosted
instances introduces:
1. Fragmented billing models and volatile infrastructure costs.
2. Fragmented identity management and inconsistent RBAC policies.
3. Credential sprawl and high risk of secret leakage.
4. Broad attack surfaces resulting from open public database ports.
5. High operational overhead to automate backups, upgrades, and telemetry.

THE MULTI-DBAAS SOLUTION:
Multi-DBaaS unifies and simplifies polyglot database management through:
- A Single Control Plane: One unified NestJS API coordinating database lifecycles.
- A Single Web Console: Next.js 16 + React 19 dashboard with Graphite/Emerald styling.
- Absolute Network Isolation: Private libvirt bridge virbr0 (192.168.122.0/24).
- Zero Public Exposure: Customer databases have no public IP and no open public ports.
- Enterprise Multi-Tenancy: Project-level role-based access control (RBAC),
  transactional quota enforcement, and AES-256-GCM credential encryption.

2. CORE ARCHITECTURAL INVARIANTS & CARDINAL PRINCIPLES
================================================================================

2.1 THE "NESTJS IS THE SINGLE GATEWAY" INVARIANT
------------------------------------------------
Traditional DBaaS providers (e.g., AWS RDS, MongoDB Atlas) provision databases
with publicly routable IP addresses or hostnames and rely on firewall allowlists
or port-level security to limit access. 

Multi-DBaaS completely inverts this model:
- Database instances LIVE EXCLUSIVELY inside an isolated private subnet
  (192.168.122.0/24 on virbr0).
- Databases have NO external IP addresses, NO public routing tables, and NO
  direct internet access.
- Customers, developers, and web clients NEVER connect directly to database
  servers over the internet via raw TCP connections (port 5432, 27017, 6333, 7474).
- The NestJS Backend is the SOLE, UNIFIED GATEWAY for both:
  1. Control-Plane Operations: VM provisioning, start, stop, restart, delete,
     credential rotation, quota accounting, and reconciliation.
  2. Data-Plane Operations: Database querying, schema inspection, document
     browsing, and mutation. All data requests transit the NestJS Data Explorer
     API over authenticated HTTPS REST endpoints and are proxied internally to
     the database engine on the private network.

Key Security & Operational Benefits:
- Zero Public Attack Surface: Network scanners, port sniffers, and automated botnets
  cannot touch database ports.
- Mandatory Authentication & RBAC on Every Operation: No query or command reaches
  the database without passing Firebase JWT validation and ProjectAuthorizationService
  permission checks.
- Comprehensive Centralized Metering: All operations flow through the gateway,
  enabling exact query telemetry, rate limiting, and quota enforcement.
- Immutable Audit Logging: Every operation produces a verifiable audit record.

2.2 STRICT 404 DISCLOSURE POLICY (DEFENSE-IN-DEPTH)
----------------------------------------------------
To protect against multi-tenant reconnaissance, identifier probing, and metadata
harvesting:
- If a user requests a resource (DatabaseInstance, Project, Operation, Event) that
  belongs to Project B while authenticated under Project A, the API strictly returns
  HTTP 404 Not Found (NEVER HTTP 403 Forbidden).
- If a user attempts to access a project UUID to which they have not been added as
  a member, the API returns HTTP 404 Not Found.
- HTTP 403 Forbidden is reserved strictly for authenticated members of a project
  who possess insufficient role privileges (e.g., a MEMBER attempting to delete a DB).
- Effect: Unauthorized users and external attackers cannot determine whether a given
  UUID exists on the platform.

2.3 IMMUTABLE INFRASTRUCTURE FIELDS & TAMPER RESISTANCE
------------------------------------------------------
Public REST API update requests (PUT/PATCH) accept only customer-editable metadata
(such as the human-readable `name` and `description`).
The backend rejects or strips any attempt to modify low-level infrastructure attributes:
- `vmId`, `internalIp`, `internalNetwork`, `host`, `port`, `status`, `failureReason`,
  `cpuCores`, `ramMb`, and `storageMb` are IMMUTABLE via public endpoints.
- These fields can only be modified internally by the trusted BullMQ lifecycle
  consumers (`DatabaseLifecycleConsumer`, `ProjectLifecycleConsumer`) and the
  underlying infrastructure providers.

4. NETWORK TOPOLOGY & ISOLATION MODEL
================================================================================

4.1 PRIVATE BRIDGE VIRBR0 & SUBNET (192.168.122.0/24)
Multi-DBaaS eliminates multi-hop routing, overlay complexities, and fragile router
VMs by standardizing entirely on the native Linux KVM bridge (`virbr0`):
- Network Name: `default` libvirt virtual network.
- Subnet: `192.168.122.0/24`.
- Subnet Mask: `255.255.255.0`.
- Gateway & DNS: `192.168.122.1` (Ubuntu Host).

4.2 IP ADDRESS ASSIGNMENT MATRIX
| IP Address | Component | Scope / Description |
|---|---|---|
| 192.168.122.1:8081 | Ubuntu Host (dbaas-host-api) | Hypervisor API for virsh domain operations |
| 192.168.122.7:8080 | Provision VM (Management Node)| Central provisioning coordinator |
| 192.168.122.10 - 254| Customer Project & DB VMs     | Isolated customer database instances |
| Dynamic (External) | NestJS Gateway (dbaas-api)    | Dual-homed: public HTTPS + internal virbr0 |

4.3 ELIMINATION OF PUBLIC DB EXPOSURE & ATTACK VECTORS
- No iptables/nftables port forwarding rules are created from public interfaces to
  internal database ports.
- Attempting to connect to `192.168.122.x` from the internet fails at the routing
  level because RFC 1918 private subnets are non-routable on the public internet.
- Zero credential exposure: Even if an adversary intercepts a customer's encrypted
  or decrypted database password, they cannot connect unless they have local network
  access inside the private hypervisor bridge.

6. IDENTITY, AUTHENTICATION & MULTI-TENANT RBAC
================================================================================

6.1 FIREBASE AUTHENTICATION & JWT VALIDATION WORKFLOW
1. The client signs in via Firebase Web SDK on the frontend using email/password or
   Google OAuth.
2. Firebase returns an ID Token (cryptographically signed JSON Web Token).
3. The client attaches this token in the `Authorization: Bearer <token>` header on
   every request to the NestJS Gateway.
4. The NestJS `FirebaseAuthGuard` extracts the token, invokes `admin.auth().verifyIdToken()`,
   and decodes claims (`uid`, `email`, `name`, `picture`).
5. The `CurrentUser` decorator injects the validated `FirebaseUser` payload into the
   request context.

6.2 USER SYNCHRONIZATION WITH PLATFORM POSTGRESQL
To ensure relational integrity and high-performance joins, the `UsersService` executes
an atomic upsert on first request:
```typescript
await this.prisma.user.upsert({
  where: { firebaseUid: firebaseUser.uid },
  update: { email: firebaseUser.email, name: firebaseUser.name },
  create: {
    firebaseUid: firebaseUser.uid,
    email: firebaseUser.email,
    name: firebaseUser.name,
    role: PlatformRole.USER,
  },
});
```
This guarantees that a local relational `User` record (with UUID `id`) always exists.

6.3 MULTI-TENANT ROLE-BASED ACCESS CONTROL (RBAC)
Resources (Databases, Credentials, Operations, Events) never exist in a global vacuum;
they belong to a `Project`.

Platform Roles (Global):
- USER: Standard authenticated developer.
- ADMIN: Global platform administrator with multi-tenant system oversight.

Project Roles (Multi-Tenant):
- OWNER:
  * Full control over the project and all resources.
  * Can delete the project, modify subscription/billing, and manage all members.
  * Can provision, start, stop, restart, delete databases, and rotate credentials.
- ADMIN:
  * Can provision, start, stop, restart, delete databases, and rotate credentials.
  * Can invite and remove standard members.
  * CANNOT delete the project, transfer ownership, or invite other Admins.
- MEMBER:
  * Operational access.
  * Can view database metadata, status, operations, events, metrics, and logs.
  * Can view decrypted connection parameters and query the Data Explorer.
  * CANNOT execute lifecycle actions (start, stop, delete, rotate credentials).
- VIEWER:
  * Read-only observability access to metrics and audit logs.

6.4 TEAM MEMBERSHIP & PROJECT INVITATION LIFECYCLE
1. An Owner or Admin submits `POST /api/v1/projects/:projectId/members` with the
   invitee's email and desired role.
2. The system generates a cryptographically secure invitation token (UUID/hex) and
   records a `ProjectInvitation` with an expiration date (default 7 days).
3. When the recipient logs in and accepts (`POST /api/v1/projects/:projectId/invitations/accept`),
   the transaction creates a `ProjectMember` record with unique constraint `[userId, projectId]`
   and marks the invitation `ACCEPTED`.

7. SUBSCRIPTION TIERS & TRANSACTIONAL QUOTA ENFORCEMENT
================================================================================

7.1 SUBSCRIPTION TIERS MATRIX
Multi-DBaaS provides three subscription tiers with strictly enforced capacity quotas:

| Subscription Tier | Max Databases | Max vCPU Cores | Max RAM (MB) | Max Storage (MB) |
|---|---|---|---|---|
| FREE              | 2 Databases   | 4 Cores        | 4,096 MB (4 GB)| 20,480 MB (20 GB)|
| BASIC             | 5 Databases   | 16 Cores       | 16,384 MB (16 GB)| 102,400 MB (100 GB)|
| PRO               | 20 Databases  | 64 Cores       | 65,536 MB (64 GB)| 512,000 MB (500 GB)|

7.2 ATOMIC SERIALIZABLE TRANSACTION ENFORCEMENT
To prevent race conditions where concurrent API requests exceed quota limits, quota
checks and database record creation execute atomically inside a PostgreSQL transaction:
```typescript
await this.prisma.$transaction(async (tx) => {
  await this.quotaService.validateQuotaWithinTransaction(tx, projectId, {
    type: dto.type,
    cpuCores: dto.cpuCores,
    ramMb: dto.ramMb,
    storageMb: dto.storageMb,
  });

  const newInstance = await tx.databaseInstance.create({ ... });
  const newOp = await tx.databaseOperation.create({ ... });
});
```

7.3 RESOURCE USAGE AGGREGATION & ROLLBACK
Within the transaction:
1. Active databases are filtered: `projectId = :pId AND status != 'DELETED'`.
2. Existing allocations are aggregated:
   - `COUNT(id)` -> Total active instances
   - `SUM(cpuCores)` -> Total allocated vCPU
   - `SUM(ramMb)` -> Total allocated RAM
   - `SUM(storageMb)` -> Total allocated storage
3. The requested profile is added to the active sum.
4. If `(currentCount + 1 > maxDatabases)` or any resource exceeds tier limits, the
   transaction rolls back immediately with HTTP 400 Bad Request (`QuotaExceededException`).
5. Hardware resources are never overcommitted.

8. ASYNCHRONOUS LIFECYCLE FINITE STATE MACHINE (FSM)
================================================================================

8.1 DATABASE LIFECYCLE STATE MACHINE (FSM)
Provisioning and managing virtualized database environments involves multi-second
I/O operations (cloning virtual disks, allocating bridges, guest OS booting). The
system uses an asynchronous Finite State Machine:

```
                    ┌────────────────────────┐
                    │   POST /databases      │
                    └───────────┬────────────┘
                                │ (Quota Validated)
                                ▼
                    ┌────────────────────────┐
       ┌───────────►│       REQUESTED        │───────────┐
       │            └───────────┬────────────┘           │
       │ Retry                  │ BullMQ Worker picks up │
       │                        ▼                        │
       │            ┌────────────────────────┐           │
       │            │      PROVISIONING      │           │
       │            └───────────┬────────────┘           │
       │                        │                        │
       │       Health Check OK  │  Health Check Failed   │
       │       ┌────────────────┴────────────────┐       │
       │       ▼                                 ▼       ▼
       │ ┌───────────┐                     ┌───────────┐
       │ │  RUNNING  │                     │   ERROR   │
       │ └─────┬─────┘                     └─────┬─────┘
       │       │                                 │
       │       │ Stop                            │ DELETE /databases/:id
       │       ▼                                 │
       │ ┌───────────┐                           │
       │ │ STOPPING  │                           │
       │ └─────┬─────┘                           │
       │       │ Domain Halted                   ▼
       │       ▼                           ┌───────────┐
       │ ┌───────────┐                     │ DELETING  │
       │ │  STOPPED  │                     └─────┬─────┘
       │ └─────┬─────┘                           │ Resources Scrubbed
       │       │ Start                           ▼
       │       ▼                           ┌───────────┐
       │ ┌───────────┐                     │  DELETED  │
       │ │ STARTING  │                     └───────────┘
       │ └─────┬─────┘
       │       │ Domain Booted
       └───────┴─────────────────────────────────┘
```

STATE GLOSSARY:
- REQUESTED: Metadata persisted in PostgreSQL; job enqueued in Redis BullMQ.
- PROVISIONING: Worker is allocating disk images, network interfaces, and booting domain.
- RUNNING: Hypervisor domain active, database engine responding to health pings.
- STOPPING: Graceful shutdown signal (ACPI shutdown / SIGTERM) dispatched.
- STOPPED: VM halted; virtual disk and persistent storage preserved intact.
- STARTING: Re-booting existing virtual domain from preserved disk.
- RESTARTING: Reboot signal transmitted to guest domain.
- DELETING: Deprovisioning VM, releasing IP, scrubbing disk volumes.
- DELETED: Soft-deleted database record (`deletedAt` populated); infrastructure wiped.
- ERROR: Hardware or provisioning failure recorded; error reason stored in `failureReason`.

8.2 ASYNCHRONOUS PROVISIONING SEQUENCE
1. Client sends `POST /api/v1/projects/:projectId/databases`.
2. Controller parses and validates input with `ZodValidationPipe`.
3. `ProjectAuthorizationService` validates user permissions (OWNER or ADMIN).
4. `DatabaseQuotaService` validates capacity within a serializable transaction.
5. `DatabaseInstance` is created in `REQUESTED` state; `DatabaseOperation` is created
   in `PENDING` state.
6. A `provision-database` job is pushed to the BullMQ `database-lifecycle` queue.
7. Gateway immediately returns HTTP 201 Created containing `databaseId` and `operationId`.
   The HTTP request is NOT blocked.
8. The `DatabaseLifecycleConsumer` background worker claims the job:
   - Updates `DatabaseOperation` -> `IN_PROGRESS`.
   - Transitions `DatabaseInstance` -> `PROVISIONING`.
   - Generates strong random 32-character hexadecimal password.
   - Encrypts password via AES-256-GCM and stores in `DatabaseCredential`.
   - Calls `IInfrastructureProvider.provisionDatabaseVm()`.
   - Executes readiness health checks against the database port.
   - Transitions `DatabaseInstance` -> `RUNNING`.
   - Updates `DatabaseOperation` -> `COMPLETED`.
   - Records an immutable `DatabaseEvent` (`STARTED`).

8.3 BULLMQ DISTRIBUTED QUEUES
- Queue Names: `project-lifecycle`, `database-lifecycle`.
- Retry Logic: Configured with 3 attempts and exponential backoff (`delay: 2000ms`).
- Concurrency: Background workers process jobs asynchronously across available CPU cores.

9. DUAL PROVISIONING MODELS
================================================================================
Multi-DBaaS supports two distinct infrastructure provisioning paradigms to balance
isolation, resource density, and provisioning speed:

9.1 MODEL A: DEDICATED CUSTOMER DATABASE VM PROVISIONING
In this model, every database instance receives its own dedicated KVM virtual machine:
- Provisioning Flow:
  1. `DatabaseLifecycleConsumer` calls `IInfrastructureProvider.provisionDatabaseVm()`.
  2. Provider contacts Provision VM (`192.168.122.7:8080`) or Host API (`192.168.122.1:8081`).
  3. Hypervisor creates a copy-on-write QCOW2 overlay from the certified base image
     (`dbaas-image-postgres-16-v1.qcow2`).
  4. Hypervisor defines domain via libvirt XML specifying allocated vCPU, RAM, and disk.
  5. Domain boots on `virbr0` and obtains internal IP via DHCP or static lease
     (e.g., `192.168.122.15`).
  6. Health check validates engine port; state moves to `RUNNING`.
- Benefits: Absolute hardware isolation, dedicated Linux kernel, independent OS metrics.

9.2 MODEL B: PROJECT HOST VM WITH IN-VM DIRECT PROVISIONING
In this optimized multi-tenant model, each Project provisions a dedicated Project Host VM,
and databases within that project are provisioned inside the running Host VM:
- Provisioning Flow:
  1. When a Project is created, `ProjectsService` enqueues `provision-project-vm`.
  2. A dedicated Project VM is provisioned on `virbr0` with project resources (e.g.,
     2 vCPU, 4096 MB RAM, 20 GB Disk, IP `192.168.122.10`).
  3. When a database is requested inside the project (`createDatabase`), the backend
     checks if `project.status === 'RUNNING'` and `project.internalIp` exists.
  4. The NestJS backend connects directly to the Project VM engine over the private
     network via `provisionInVmDatabase()`:
     - For PostgreSQL: Connects as `dbaas_admin`, creates dedicated role (`usr_<name>`)
       with encrypted password, creates database (`<name>`), and grants all privileges.
     - For MongoDB: Connects to MongoDB admin DB, creates database user with `dbOwner`
       role scoped to the specific target database.
  5. The database record is immediately marked `RUNNING`.
- Benefits: Instantaneous database creation (< 500ms), high density, lower hardware overhead.

11. CREDENTIAL SECURITY & DATA PROTECTION
================================================================================

11.1 AES-256-GCM SYMMETRIC ENCRYPTION
Database passwords and connection credentials are protected using industry-standard
AES-256-GCM (Galois/Counter Mode) authenticated encryption:
- Algorithm: `aes-256-gcm`.
- Encryption Key: 256-bit (32-byte) key derived using SHA-256 from `ENCRYPTION_KEY`.
- Nonce / IV: 12-byte cryptographically secure random Initialization Vector (`crypto.randomBytes(12)`).
- Integrity Tag: 16-byte Authentication Tag (`cipher.getAuthTag()`).
- Storage Format in `database_credentials.encrypted_password`:
  `iv_hex:auth_tag_hex:ciphertext_hex`
- Plaintext passwords NEVER touch disk storage.

11.2 DECRYPTED CREDENTIAL RETRIEVAL
When an authorized Project Owner or Admin requests connection parameters via
`GET /api/v1/projects/:projectId/databases/:databaseId/connection`:
1. The backend authorizes the caller's role.
2. It fetches the active credential record from `database_credentials`.
3. `EncryptionService.decrypt()` splits the stored string into IV, auth tag, and ciphertext.
4. The decipher validates the authentication tag. If ciphertext was tampered with,
   decryption throws an exception.
5. The decrypted password is reconstituted into standard connection strings:
   - PostgreSQL: `postgresql://<user>:<password>@<internalIp>:5432/<dbname>`
   - MongoDB: `mongodb://<user>:<password>@<internalIp>:27017/<dbname>?authSource=admin`
   - Qdrant: `http://<user>:<password>@<internalIp>:6333`
   - Neo4j: `neo4j://<internalIp>:7474`

11.3 DYNAMIC CREDENTIAL ROTATION
When an administrator triggers `POST .../credentials/rotate`:
1. System validates that the database is in `RUNNING` status.
2. Generates new random 16-byte hex password.
3. If running inside a Project VM, updates the password directly in PostgreSQL (`ALTER USER`)
   or MongoDB (`updateUser`).
4. In a transactional write:
   - Marks previous active credential record `isActive = false`.
   - Inserts new `DatabaseCredential` with `isActive = true`.
   - Records `DatabaseEvent` (`CREDENTIALS_ROTATED`).

11.4 AUDIT LOGGING SUBSYSTEM
Every critical administrative and security action generates an immutable `AuditLog` entry:
- Fields: `userId`, `projectId`, `action`, `resource`, `resourceId`, `metadata`,
  `ipAddress`, `userAgent`, `createdAt`.
- Monitored Actions: Project creation/deletion, member addition/removal, database
  provisioning/deletion, credential rotations, subscription modifications.

4. Command Injection Prevention:
   - NEVER invokes arbitrary shell strings or `exec()`.
   - Uses `child_process.execFile('/usr/bin/virsh', argsArray)` with strict argument arrays.
